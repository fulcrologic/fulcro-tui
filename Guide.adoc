= Getting Started

Fulcro normally renders through React into the browser DOM. `fulcro-tui` is an
*alternative rendering target*: instead of DOM, your components produce a tree of
terminal-native nodes (boxes, text, inputs, buttons), which the library lays out
and paints into a character-cell buffer displayed in a real terminal via
https://github.com/jline/jline3[JLine].

The payoff: you write ordinary Fulcro components with the stock `defsc` macro, use
the same data-management primitives (normalized state, mutations, transactions),
and get a React-like terminal UI. Because the whole pipeline is plain Clojure (no
React, no DOM, no ClojureScript), it runs on the JVM and under
https://babashka.org/[babashka].

NOTE: This library is *alpha* — not yet API-stable — but the UI machinery is solid
and the Fulcro patterns it builds on have been stable for years. Expect any changes
to be minor.

[IMPORTANT]
====
*The Fulcro API is the API.* `fulcro-tui` is **just a rendering target** — you build a
normal Fulcro app (`defsc` components, queries, idents, normalized state, mutations,
`comp/transact!`, `:initial-state`) and this library only changes where it draws: a
terminal instead of the DOM. There are no TUI replacements for Fulcro's data or
transaction APIs.

So this guide assumes you already know Fulcro — for Fulcro proper, see the *Fulcro
Developer's Guide* at https://book.fulcrologic.com[book.fulcrologic.com]. What follows
covers only what is specific to the terminal target: the *elements* you render in place
of DOM, layout, focus/keyboard, and the run loop.
====

== What you need

Add the dependency (use the latest version from the badge on the project README):

[source,clojure]
-----
{:deps {com.fulcrologic/fulcro-tui {:mvn/version "RELEASE"}}}
-----

This transitively brings in `com.fulcrologic/fulcro` and `org.jline/jline`. No
ClojureScript toolchain is required — everything here is `.clj`.

== The namespaces and their aliases

The library is organized into a handful of namespaces. This guide uses the same
aliases the real source and tests use:

[cols="2,1,3"]
|===
| Namespace | Alias | What's in it

| `com.fulcrologic.fulcro.tui.elements`    | `elements` | Element generators (`vbox`, `text`, …) and `focused?`.
| `com.fulcrologic.fulcro.tui.engine`      | `engine`   | Node model, render pipeline, layout/paint, focus & scroll state.
| `com.fulcrologic.fulcro.tui.application` | `app`      | The application lifecycle and terminal driver.
| `com.fulcrologic.fulcro.tui.terminal`    | `term`     | The `Terminal` abstraction and key-event model.
| `com.fulcrologic.fulcro.tui.inspect`     | `tui-inspect` | Debug-only Fulcro Inspect connector.
|===

== The shape of a TUI app

Every `fulcro-tui` program has the same three moving parts:

. A *root component* — a normal `com.fulcrologic.fulcro.components/defsc` whose
  `:render` returns a tree of TUI *nodes* (built with the element generators
  `vbox`, `hbox`, `text`, `input`, `button`, …) instead of DOM.
. A *Fulcro application* — built with `app/application`, which wires a synchronous
  Fulcro app whose every state change repaints the terminal.
. An *input loop* — `app/mount!` / `app/run-blocking!` attaches a terminal and runs
  the keyboard loop; `app/quit!` stops it.

In code:

[source,clojure]
-----
(ns my.tui
  (:require
    [com.fulcrologic.fulcro.components :as comp]
    [com.fulcrologic.fulcro.tui.elements :as elements]
    [com.fulcrologic.fulcro.tui.application :as app]))

(comp/defsc Root [this {:keys [greeting]}]
  {:query         [:greeting]
   :initial-state {:greeting "Hello, terminal!"}}     ; <1>
  (elements/vbox {:padding 1 :border? true}
    (elements/text {:bold true :color :cyan} (or greeting ""))
    (elements/text {:color :bright-black} "Press Ctrl-Q to quit.")))

(defn -main [& _]
  (app/start! {:root-class Root}                                  ; <2>
              {:global-keymap {[:ctrl "q"] (fn [a _e] (app/quit! a))}})) ; <3>
-----
<1> Declare the root's starting data with `:initial-state` (the idiomatic Fulcro
    way — it composes down through child components and survives refactoring).
<2> `app/start!` is the one-call entrypoint: it builds the app *and* runs it to
    completion. It seeds the db from the root class's `:initial-state` *by default*
    — no extra option needed. (Opt out with `:initial-state false`.)
<3> The second (optional) map is run options — here a global keymap that wires
    *Ctrl-Q* to quit. See <<_the_application_lifecycle,The Application Lifecycle>>
    for the lower-level `application` → `run-blocking!` two-step.

== Run the demo

The repository ships a complete, runnable demo at
`src/tui-example/tui_example/form.clj`: a two-field form with a multiline notes
area, a Save button, a scrolling list, a confirmation modal, and a fruit picker.
Run it in a real terminal on the JVM:

[source,bash]
-----
clojure -M:tui -m tui-example.form
-----

…or under babashka (faster startup, no JVM):

[source,bash]
-----
bb run tui
-----

Controls: *Tab* / *Shift-Tab* move focus, type to edit the focused field, *Enter* /
*Space* activates a button or list item, *PageUp* / *PageDown* scroll the list, and
*Ctrl-Q* quits.

The full demo source is the best reference for "real" usage and is referenced
throughout this guide. It is reproduced in full in

= Elements: the building blocks

Instead of DOM, your components return a tree of *elements* — boxes, text, inputs,
buttons — built with the generators in `com.fulcrologic.fulcro.tui.elements`. This
chapter is the catalog of what you can put on screen and how you call the generators.

== Calling convention

Every generator takes an optional leading *attribute map*, then any number of children:

[source,clojure]
-----
(elements/vbox {:padding 1 :border? true}       ; <1>
  (elements/text {:color :cyan} "Name:")         ; <2>
  (elements/text {} "value")
  "a bare string is a text child")               ; <3>
-----
<1> The first argument, if it is a map, is the element's attributes — layout, style,
    and event handlers. Omit it for defaults.
<2> Remaining arguments are children: other elements…
<3> …or bare strings/numbers, which become text. `nil` children are dropped, and nested
    sequential collections (e.g. the result of `map`/`for`) are flattened in, so you can
    splice a generated list of children directly.

== The element catalog

[cols="1,4"]
|===
| Generator | What it gives you

| `elements/vbox`     | A container that stacks its children *vertically*. See <<_layout,Layout>>.
| `elements/hbox`     | A container that stacks its children *horizontally*. See <<_layout,Layout>>.
| `elements/box`      | A single styling/padding/border container; its child fills the content area.
| `elements/text`     | Text (its string/number children), optionally wrapped to its width. See <<_text_inputs_multiline,Text>>.
| `elements/input`    | An editable text field — single-line or multiline. See <<_text_inputs_multiline,Inputs>>.
| `elements/button`   | An activatable control; its children are the label. See <<_buttons_focus_keyboard,Buttons>>.
| `elements/line`     | A horizontal or vertical rule.
| `elements/viewport` | A fixed-size window whose larger child *scrolls* within it. See <<_viewports_scrolling,Viewports>>.
| `elements/modal`    | An overlay window floated on top of the rest of the UI. See <<_modals_pickers,Modals>>.
| `elements/picker`   | A ready-made list picker built on `modal`. See <<_modals_pickers,Pickers>>.
|===

TIP: `elements/input` takes a single attributes map and *no* children — inputs are
*controlled*, so their text comes from the `:value` attribute, not from child nodes.

`elements/focused?` (whether the element with a given id currently has focus) rounds out
the namespace. Everything else — running mutations, querying, app state — is plain Fulcro
(`comp/transact!` and friends); see <<_triggering_change,Triggering change>>.

[NOTE]
====
Under the hood each generator just returns a plain map and the driver walks that tree to lay it out
and paint it — you never build or inspect those maps to *use* the library. To add a brand-new
low-level element of your own (a custom painting primitive, not a composition), see
<<_extending_custom_rendered_elements,Extending: custom rendered elements>>. The node vocabulary and
the render pipeline (`engine/render-tree`/`render-root`/`render-buffer`/`screen`) are covered under
<<_testing_headless,Testing / Headless>>.
====

= Defining Components

TUI components are *ordinary* Fulcro components — there is no special macro. Define them
with the stock `com.fulcrologic.fulcro.components/defsc`; `:query`, `:ident`,
`:initial-state`, and the rest of `defsc`'s options behave exactly as in a browser
Fulcro app (they are about *data*, see the
https://book.fulcrologic.com[Fulcro Developer's Guide]). The only difference is that the
`:render` body returns a tree of elements (from the previous chapter) instead of DOM.

== A minimal component

[source,clojure]
-----
(comp/defsc Greeting [this {:keys [greeting]}]
  {:query [:greeting]}
  (elements/vbox {:padding 1}
    (elements/text {:bold true} (or greeting ""))))
-----

== Children of components

To render a child component, build a factory for it and call it inside your render,
then place the result among your nodes:

[source,clojure]
-----
(def ui-greeting (comp/factory Greeting))           ; <1>

(comp/defsc Root [this props]
  {:query [{:greeting (comp/get-query Greeting)}]}
  (elements/vbox {}
    (ui-greeting (:greeting props))))               ; <2>
-----
<1> Use Fulcro's stock `comp/factory` (and `comp/computed-factory` when you need to
    pass a computed map). The TUI walker recognizes the instances they produce.
<2> Call the factory in render; the walker replaces the instance with its rendered
    node subtree.

NOTE: There is no TUI-specific `factory`/`computed-factory` — use Fulcro's stock
`comp/factory` / `comp/computed-factory`. The driver recognizes the instances they
produce and renders each in place.

== Triggering change

There is nothing TUI-specific here: an element's event handler updates state by calling
Fulcro's own `com.fulcrologic.fulcro.components/transact!` with a mutation, exactly as in
any Fulcro app (see the https://book.fulcrologic.com[Fulcro Developer's Guide] for
defining and dispatching mutations).

[source,clojure]
-----
(elements/button {:id          :save
                  :on-activate (fn [] (comp/transact! this [(set-field {:k :form/saved? :v true})]))}
  " Save ")
-----

Because the app is built with *synchronous* transactions and a render hook, the
transaction runs and the screen repaints before control returns.

= Layout

Containers divide space along one axis and let children fill the other. Sizing is
declared with attributes on each child.

== Boxes and stacking

* `elements/vbox` stacks children top-to-bottom, dividing *height* among them; each
  child fills the box *width* unless it declares its own.
* `elements/hbox` stacks children left-to-right, dividing *width*; each fills the
  *height*.
* `elements/box` is a single styling/padding/border container; each child fills its
  content area (useful for borders/padding around one thing).

== Sizing attributes

On a child of a `vbox`/`hbox`, the *main-axis* size (height in a vbox, width in an
hbox) is resolved from these attributes, in order of precedence:

[cols="1,4"]
|===
| Attribute | Meaning

| `:width` / `:height` (integer) | A fixed cell count.
| `:width` / `:height` `:half`   | Half the available extent.
| `:width` / `:height` `[:fraction f]` | The fraction `f` (0.0–1.0) of the extent, rounded.
| `:grow <weight>` | Share the leftover space after fixed/fraction/content children, split by weight.
| (none) | Fall back to the child's *intrinsic* (content-driven) size.
|===

`:grow` children divide whatever is left after the fixed- and content-sized children
are placed. Multiple grow children split by their relative weights.

On the *cross axis*, a child fills the track by default; if it declares a cross-axis
size, `:align` (`:start` / `:center` / `:end`, with `:middle`/`:right`/`:bottom`
aliases) positions it within the track.

[source,clojure]
-----
(elements/hbox {:height 1}
  (elements/text {:width 8 :color :cyan} "Name:")   ; <1>
  (elements/input {:id :name :grow 1 :value v}))     ; <2>
-----
<1> A fixed 8-column label.
<2> The input grows to fill the rest of the row.

== Borders and padding

`:border?` draws a single-cell box-drawing border; `:padding` (a non-negative
integer) insets the content on every edge. Both shrink the content area available to
children. `:min-width` / `:min-height` set a floor on a node's size.

== Style attributes

Style attributes apply to a node and its painted text:

[cols="1,4"]
|===
| Attribute | Meaning

| `:color <kw>`   | Foreground color (a palette keyword, e.g. `:cyan`, `:bright-white`).
| `:bg <kw>`      | Background color.
| `:bold true`    | Bold text.
| `:highlight true` | Reverse video (used to show focus/selection).
|===

The color palette is the 16 ANSI colors: `:black :red :green :yellow :blue
:magenta :cyan :white` and their `:bright-*` variants. See `engine/palette`.

== Viewports (scrolling)

A `:viewport` is a *fixed-size* container whose single (potentially larger) child is
laid out at its natural size and scrolls within the viewport's bounds. Give it a
fixed `:height` (and/or `:width`) and an `:id` (so its scroll position can be
tracked):

[source,clojure]
-----
(elements/viewport {:id :items :height 6 :border? true}
  (elements/vbox {}
    (for [i (range 15)]
      (elements/button {:id (keyword (str "item-" i)) :highlight (elements/focused? (keyword (str "item-" i)))}
        (str "Item " i)))))
-----

The driver auto-scrolls a viewport to keep the focused child visible (Tab/Arrows),
and PageUp/PageDown page through it. See
<<_buttons_focus_keyboard,Buttons, Focus & Keyboard>>.

= Text, Inputs & Multiline

== Text and wrapping

`elements/text` renders its string/number children as text. By default text is *not*
wrapped — embedded newlines (`\n`) break lines, but a long line is clipped to its
width. Set `:wrap true` to word-wrap to the node's content width:

[source,clojure]
-----
(elements/box {:width 40 :height 5 :border? true}
  (elements/text {:wrap true} "This paragraph wraps to its fixed-width box."))
-----

Wrapping is width-aware: it measures display columns (`engine/string-width`), so wide
(East-Asian/emoji) and zero-width characters are handled correctly, never split
across a cell boundary.

== Single-line inputs

`elements/input` is a *controlled* field: its text comes from `:value` and edits flow
out through `:on-change`. You store the value in app state and feed it back in:

[source,clojure]
-----
(elements/input {:id        :email
                 :grow      1
                 :value     (or email "")
                 :on-change (fn [v _caret]
                              (comp/transact! this [(set-field {:k :form/email :v v})]))})
-----

The handler-arg conventions for input-related attributes are:

[cols="1,3"]
|===
| Attribute | Called as

| `:on-change` | `(handler new-value new-caret)`
| `:on-submit` | `(handler current-value)` — fired on *Enter* in a single-line input.
| `:on-key`    | `(handler key-event)`
| `:on-activate` | `(handler)` — no args.
| `:on-focus` / `:on-lost-focus` | `(handler id)`
|===

The caret position is tracked for you in a transient runtime store. If you prefer to
own the caret in state, set a `:caret` attribute and manage it yourself.

== Multiline inputs

Add `:multiline? true` (and usually a fixed `:height`) for a text-area. The value is
a single string that may contain `\n`; it wraps to the input's width, the arrow keys
move the caret (Up/Down by *visual* line), and *Enter inserts a newline* (it does not
submit). The box self-scrolls to keep the caret visible.

[source,clojure]
-----
(elements/input {:id         :notes
                 :multiline? true
                 :height     4
                 :value      (or notes "")
                 :on-change  (fn [v _caret]
                               (comp/transact! this [(set-field {:k :form/notes :v v})]))})
-----

== Buffered typing (debounced `:on-change`)

A fully controlled input pays for the whole `:on-change` round-trip — a transaction plus
whatever it triggers (re-render, filtering, a load) — on *every* keystroke before the typed
character can echo. On a busy screen that reads as typing lag.

`:change-debounce-ms N` (N > 0) opts an input into engine-buffered editing:

[source,clojure]
-----
(elements/input {:id                 :notes
                 :multiline?         true
                 :height             4
                 :change-debounce-ms 150
                 :value              (or notes "")
                 :on-change          (fn [v _caret]
                                       (comp/transact! this [(set-field {:k :form/notes :v v})]))})
-----

Each edit echoes immediately from a transient buffer in the runtime atom, and `:on-change`
fires with the latest value once no key has arrived for N ms. The buffer is *flushed* — the
pending `:on-change` invoked now, the buffer dropped — when focus leaves the input and on
*Enter* in a single-line input (before `:on-submit`), so app state is consistent at every
interaction boundary. Between keystrokes the model lags the screen by at most N ms.

Controlled semantics are preserved by reconciliation: if the prop catches up to the buffer
(your own debounced commit landed) the buffer is dropped as redundant; if the prop changes to
something *else* (an external mutation — a load, a reset) the buffer is dropped, its pending
commit is cancelled, and the prop wins.

To turn this on for a whole app, pass `:default-change-debounce-ms` to `application` — it
applies to every input that does not set its own attr, and an individual input opts back out
with an explicit `:change-debounce-ms 0`:

[source,clojure]
-----
(app/application {:root-class                 Root
                  :initial-state              true
                  :default-change-debounce-ms 150})
-----

= Buttons, Focus & Keyboard

== Buttons

`elements/button` renders its children as a label and carries an `:on-activate`
handler (called with no args) fired by *Enter* or *Space* when focused:

[source,clojure]
-----
(elements/button {:id          :save
                  :highlight   (elements/focused? :save)
                  :on-activate (fn [] (comp/transact! this [(save-form)]))}
  " Save ")
-----

== The focus model

Focus is a single piece of state: the `:id` of the focused node. A node is
*focusable* when it has an `:id` and is an `:input` or `:button`, or sets
`:focusable? true`, or carries any focus-relevant handler. The current focus drives
which node receives keys and which shows its highlight.

Within render, `elements/focused?` tells you whether a given id currently has focus
(so you can set `:highlight (elements/focused? :save)`). The focus *state* and ring
live in the `engine` namespace:

* `engine/focus!` — set the focused id (and trigger a render).
* `engine/current-focus` — read the focused id from an app or state-map.
* `engine/focus-order` / `engine/focusables` — compute the focus ring (document
  order, with an optional `:priority` attribute to reorder).

== The keyboard ring

The driver routes keys for you:

* *Tab* / *Down* → next focusable; *Shift-Tab* / *Backtab* / *Up* → previous
  (wrapping). A *multiline* input captures Up/Down for caret movement instead.
* A focused `:input` gets controlled-text editing.
* *Enter* / *Space* on a focusable with `:on-activate` activates it.
* Otherwise the key *bubbles*: the focused node's `:on-key`, then its ancestors'
  `:on-key`, then the *global keymap*.

== The global keymap

A global keymap maps a *normalized chord* to a handler `(fn [app key-event])`. A
chord is the key's keyword or 1-char string, optionally prefixed with a vector of
modifier keywords. Reserved chords like quit are dispatched at the loop level,
regardless of focus:

[source,clojure]
-----
;; via start! / run-blocking! / mount! run options:
(app/start! {:root-class Root}
            {:global-keymap {[:ctrl "q"] (fn [app _event] (app/quit! app))}})

;; …or as an app-level default, declared once on the application:
(app/application {:root-class Root
                  :global-keymap {[:ctrl "q"] (fn [app _event] (app/quit! app))}})
-----

A keymap passed at run time (`mount!`/`run-blocking!`/`start!` run options) wins;
otherwise the app-level default registered at `application`/`start!` time is used.

`engine/key-chord` computes the chord for an event; `[:ctrl "q"]` is Ctrl-Q, `:tab`
is Tab, `"a"` is the letter a. Key events themselves are normalized maps with
`:key :char :ctrl? :alt? :shift?` (and `:raw`); special keys live in
`term/special-keys` (`:enter :tab :escape :backspace :delete :up :down :left
:right :home :end :page-up :page-down :backtab`).

== Control shortcuts and the enhanced keyboard

A control can declare a `:shortcut` chord (e.g. `[:alt "s"]`) that focuses (and, for
buttons, activates) it from anywhere, with its mnemonic letter underlined in the label.
Modified chords like `Alt-s` can only be captured when the terminal supports the
*Kitty/fixterms enhanced keyboard protocol* (CSI-u). The driver probes for it at startup
and, when it is absent, the whole shortcut layer — and the mnemonic underlines — stay
*off*. kitty, ghostty, WezTerm and recent Alacritty support it out of the box.

[NOTE]
.iTerm2: turn on `Esc+` for the Option key
====
iTerm2 *answers* the CSI-u probe (so the protocol reports as enabled), but by default the
*Option* key composes a character — `Alt-s` is sent as `ß`, not as a modified key — so
shortcuts appear dead. Fix it once per profile:

*Settings → Profiles → Keys → General → Left Option key: `Esc+`* (set Right Option too if
you use it). After that `Alt-s` arrives as the CSI-u sequence `ESC [ 115 ; 3 u` and the
shortcuts fire.
====

To see exactly what your terminal sends for a chord, run the byte-level probe *in that
terminal* and press the key (it works under both `clojure` and `bb`):

[source,shell]
-----
clojure
user=> ((requiring-resolve 'com.fulcrologic.fulcro.tui.terminal/probe-key!))
-----

A conforming terminal prints `:alt? true` for `Alt-s`; a composing terminal prints a single
code point with `:alt? false`. For terminal stacks that carry CSI-u but swallow the startup
query (e.g. tmux with `extended-keys on`), force the protocol on with the
`fulcro.tui.enhanced-keys` system property (or `FULCRO_TUI_ENHANCED_KEYS` env var) set to
`force`; set it to `off` to disable.

= Modals & Pickers

== Modals

`elements/modal` is an *overlay window* the driver floats over the rest of the UI.
While a modal is open the driver *traps focus and keyboard input* to it — the controls
behind it are inert. The modal owns no lifecycle state: *you* toggle `:open?` (and
record any result) with your own mutations.

[source,clojure]
-----
(elements/modal {:id         :confirm
                 :open?      confirm-open?
                 :title      "Confirm reset"
                 :width      40 :height 7
                 :on-dismiss (fn [] (comp/transact! this [(close-confirm)]))} ; Escape calls this
  (elements/text {:wrap true} "Reset every field? This cannot be undone.")
  (elements/line {})
  (elements/hbox {:height 1 :align :center}
    (elements/button {:id :confirm-reset  :highlight (elements/focused? :confirm-reset)
                      :on-activate (fn [] (comp/transact! this [(reset-form)]))} " Reset ")
    (elements/text {:width 2} "")
    (elements/button {:id :confirm-cancel :highlight (elements/focused? :confirm-cancel)
                      :on-activate (fn [] (comp/transact! this [(close-confirm)]))} " Cancel ")))
-----

Modal attributes:

* `:open?` — the overlay is active (composited + focus-trapped) only when truthy;
  when falsy it renders nothing.
* `:width` / `:height` — a cell count or `[:fraction f]` of the screen; defaults to
  the modal's intrinsic content size.
* `:align` — `:center` (default), `:start`, or `:end`.
* `:border?` — defaults to `true`. `:title` paints a string on the top border.
* `:on-dismiss` — a zero-arg handler fired on *Escape*.

The modal node can live in your render tree at all times; it simply renders nothing
while `:open?` is falsy. Closed modals are stripped from layout and never focusable.

== Pickers

`elements/picker` is a *list picker* built on `modal`: a scrollable viewport of
selectable rows where the focused row *is* the highlighted choice. Up/Down move the
highlight (the list scrolls to follow), Enter selects, Escape cancels.

[source,clojure]
-----
(elements/picker {:id        :fruit
                  :open?     picker-open?
                  :title     "Pick a fruit"
                  :width     24 :height 8
                  :options   [{:value :apple :label "Apple"}
                              {:value :pear  :label "Pear"}]
                  :on-select (fn [v] (comp/transact! this [(choose-fruit {:v v})]))
                  :on-cancel (fn []  (comp/transact! this [(close-picker)]))})
-----

`:options` is a vector of `{:value … :label …}` maps; `:on-select` is called with a
row's `:value`; `:on-cancel` is wired to the modal's `:on-dismiss` (Escape). Like a
modal, it is a pure composition of existing nodes — state and selection are yours.

= The Application Lifecycle

The lifecycle namespace is `com.fulcrologic.fulcro.tui.application` (alias `app`). It
builds the Fulcro application and runs the terminal driver loop.

== The one-call entrypoint: `start!`

For the common case, `app/start!` does everything — build the app and run it to
completion (blocking until the loop ends):

[source,clojure]
-----
(app/start! {:root-class Root}                                  ; <1>
            {:global-keymap {[:ctrl "q"] (fn [a _e] (app/quit! a))}}) ; <2>
-----
<1> *App options* — the same map `app/application` takes (`:root-class`,
    `:initial-state`, `:remotes`, `:global-keymap`, `:inspect?`).
<2> *Run options* (optional) — the same map `app/mount!`/`app/run-blocking!` take
    (`:terminal`, `:global-keymap`, `:on-error`).

`(app/start! app-opts run-opts)` is exactly
`(app/run-blocking! (app/application app-opts) run-opts)`. Reach for the two-step form
below only when you need a handle on the app *before* the loop starts (e.g. to seed
state manually, or to mount on a custom terminal in a test).

== Building the app

`app/application` returns a synchronous raw Fulcro app whose every state change
repaints the terminal (once a terminal is attached):

[source,clojure]
-----
(app/application
  {:root-class    Root          ; <1>
   :initial-state false          ; <2>
   :remotes       {...}          ; <3>
   :global-keymap {...}          ; <4>
   :inspect?      false})        ; <5>
-----
<1> *Required.* The TUI root component class (a stock `comp/defsc`).
<2> Initialize app state from the root class's `:initial-state`. *Defaults to
    `true`* — pass `false` only to opt out (e.g. when you seed the db yourself).
<3> Optional Fulcro remotes map (for talking to a server).
<4> Optional *app-level default* global keymap (chord → `(fn [app key-event])`).
    `mount!`/`run-blocking!`/`start!` use it unless given their own `:global-keymap`,
    so you can declare a quit chord once here instead of repeating it per run.
<5> Debug-only Fulcro Inspect hook — see <<_debugging_with_fulcro_inspect>>.
    Defaults to the `tui.inspect` system property.

=== Recommended: declare `:initial-state` on the Root

The idiomatic Fulcro way to seed app state is to declare `:initial-state` on the
root component (composing it down through children). Because `app/application`
initializes from the root by default, that is *all* you need:

[source,clojure]
-----
(comp/defsc Root [this props]
  {:query         [:greeting]
   :initial-state {:greeting "Hello, terminal!"}}  ; a map, or (fn [params] ...)
  ...)

(app/application {:root-class Root})   ; initialized from Root :initial-state by default
-----

This is the canonical, default behavior — it survives refactoring and scales as you
add child components with their own initial state. It is exactly what the bundled
demo does (its `Root` declares `:initial-state (fn [_] initial-db)` and its `-main`
is just `(app/application {:root-class Root})`).

=== Quick-start escape hatch: seed the db directly

If your root keeps a flat, top-level db, you can instead pass `:initial-state false`
and `reset!` the state-atom directly. This is a quick hack for a tiny flat app; it
does not compose, so prefer the recommended form as soon as you have child
components.

NOTE: The bundled demo *no longer* uses this form — it was switched to declared
`:initial-state` on the Root (see <<demo-source,the appendix>>), which shows the
canonical pattern.

[source,clojure]
-----
(let [a (app/application {:root-class Root :initial-state false})]
  (reset! (:com.fulcrologic.fulcro.application/state-atom a) initial-db)
  ...)
-----

No terminal is attached by `application`; attach one with `mount!` or `run-blocking!`.

== Mounting and running

`app/mount!` attaches a terminal and starts the keyboard input loop on a new thread,
returning a *handle*:

[source,clojure]
-----
(app/mount! a
  {:terminal      (term/jline-terminal)   ; <1>
   :global-keymap {[:ctrl "q"] (fn [app _e] (app/quit! app))} ; <2>
   :on-error      (fn [app throwable] (println "loop died:" throwable))}) ; <3>
;; => {:app a :terminal t :thread <Thread> :running? <atom true> :error <atom nil>}
-----
<1> Optional. Defaults to a real `term/jline-terminal`; tests pass a
    `term/string-terminal`.
<2> Optional. Reserved chords dispatched at the loop level (fire regardless of focus).
    Defaults to the keymap registered on the app at `application`/`start!` time.
<3> Optional `(fn [app throwable])` called if the input loop throws. The loop also
    stashes the throwable on the handle's `:error` atom and always leaves the terminal.

The returned *handle* map is `{:app :terminal :thread :running? :error}`: `:running?`
is an atom you can set false to stop the loop, and `:error` is an atom holding any
uncaught loop exception (else `nil`) — so `run-blocking!`'s `.join` returning does not
silently hide a crash; check `@(:error handle)`.

`app/run-blocking!` is `mount!` plus a `.join` on the loop thread — it blocks until
the terminal reaches EOF or the loop is stopped. The usual `-main` simply uses
`start!`, but the two-step form is handy when you need the app first:

[source,clojure]
-----
(defn -main [& _]
  (let [a (app/application {:root-class Root})]
    ;; ... optionally inspect/seed `a` here ...
    (app/run-blocking! a {:global-keymap {[:ctrl "q"] (fn [app _e] (app/quit! app))}})
    (println "Goodbye.")))
-----

`app/quit!` stops the loop (sets `:running?` false, drops the resize handler, leaves
the terminal — which forces a blocked read to EOF — then best-effort interrupts the
thread). It accepts either the handle or the app.

== Lower-level entry points

* `app/attach!` — attach a terminal and do the initial paint, *without* starting a
  loop (you drive it yourself).
* `app/step!` — run one deterministic iteration (dispatch a key, then repaint). The
  backbone of tests.
* `app/screen-of` / `app/screen-styled-of` — read the most-recently-painted buffer
  back as row strings (or styled cell maps). Essential for headless assertions.

= Debugging with Fulcro Inspect

`fulcro-tui` apps can be observed live in the standalone *Fulcro Inspect* (Electron)
application — the same tool used for browser Fulcro apps. You get the transaction
log, network activity, and DB state/changes streaming from your terminal app.

This has been *verified end-to-end*: transactions and state changes stream to Inspect
in real time.

== How it works

In a browser, Fulcro Inspect connects over a websocket via a CLJS-only "electron
target." The JVM has no such target, so `fulcro-tui` ships a small CLJ shim,
`com.fulcrologic.fulcro.tui.inspect`, that provides the one missing piece: a
`DevToolConnectionFactory` that speaks Sente over a real websocket from the JVM. The
rest of the inspect pipeline (event generation, devtools-remote transport) is already
CLJC and ships transitively with Fulcro 3.10.x.

[IMPORTANT]
====
The shim ships *in the library* (`src/main/com/fulcrologic/fulcro/tui/inspect.clj`)
and is *debug-only*: it is never loaded by normal or babashka runs. `app/application`
resolves it lazily, via `requiring-resolve`, only when inspect is enabled — so it
costs nothing (and pulls in no `core.async`/Sente) unless you ask for it.
====

NOTE: Inspect is *JVM-only*. The connector requires `clojure.core.async` and
`taoensso.sente`, which do not run under babashka/SCI. By contrast, the TUI core
itself — the element generators and the `step!` loop driven through a
`string-terminal` — runs fine under babashka; only the Inspect connector is excluded.

== Prerequisites

. The standalone *Fulcro Inspect (Electron)* app must be *running*. It hosts the
  websocket server on *localhost:8237*.
. Inspect must be *enabled* — either pass `:inspect? true` to `app/application`, or
  set `-Dtui.inspect=true` (the `:inspect` deps alias does this). The shim itself is
  always on the classpath, since it ships in the library.

== Two ways to turn it on

=== The easy way: `add-inspect!`

The one-call entry point is `add-inspect!`:

[source,clojure]
-----
(require '[com.fulcrologic.fulcro.tui.inspect :as tui-inspect])

(tui-inspect/add-inspect! app)
-----

This single call does everything:

* *Force-enables both inspect gates at runtime* — so you do **not** need any JVM `-D`
  flags. (There are two independent gates: Fulcro's inspect gate and the
  devtools-common target gate. Both are read once at namespace load, so the shim
  flips the realized vars directly via `alter-var-root`.)
* *Installs the JVM Sente websocket factory* (`install!`).
* *Attaches Fulcro Inspect to your app* (`fulcro.inspect.tool/add-fulcro-inspect!`).

If you only need parts, the shim also exposes `tui-inspect/install!` (register the
websocket factory once) and `tui-inspect/enable!` (force the gates on) separately.

=== Through the app builder

`app/application` accepts an `:inspect?` option that, when truthy, lazily resolves and
calls `add-inspect!` for you:

[source,clojure]
-----
(app/application {:root-class Root :inspect? true})
-----

Its default is the value of the `tui.inspect` system property, which leads to the
most convenient workflow:

== The `:inspect` deps alias (recommended)

The project's `deps.edn` defines an `:inspect` alias that simply sets
`-Dtui.inspect=true` (the shim already ships in the library, so no extra source path
is needed):

[source,clojure]
-----
:inspect {:jvm-opts ["-Dtui.inspect=true"]}
-----

Combine it with the `:tui` alias to run the demo with Inspect wired up:

[source,bash]
-----
clojure -M:tui:inspect
-----

Because `-Dtui.inspect=true` flips `app/application`'s `:inspect?` default to true,
the app calls `add-inspect!` at startup — no code change required. Just make sure the
Inspect Electron app is already running on localhost:8237.

== Troubleshooting

[cols="1,3"]
|===
| Symptom | Likely cause

| Nothing shows up in Inspect | The Electron app isn't running, or isn't on localhost:8237.
| Inspect never connects | Inspect wasn't enabled — pass `:inspect? true` or set `-Dtui.inspect=true` (use the `:inspect` alias).
| Connected once but no events | The inspect gates weren't enabled before the pipeline loaded; prefer `add-inspect!` (which `alter-var-root`s the realized vars) over setting `-D` flags after load.
| Works on JVM, fails under babashka | Inspect is JVM-only. The shim uses `core.async` go-loops and Sente; run inspect sessions on the JVM.
|===

= Measuring performance

The library ships a tiny built-in profiler, `com.fulcrologic.fulcro.tui.perf` (`perf`), modeled
on the core of https://github.com/taoensso/tufte[Tufte] — `p` profile points, a `profile` scope,
and a self-time report. It is reimplemented with plain atoms/volatiles so it runs under
*babashka* as well as the JVM (real Tufte's `encore` dependency does not load under SCI). The
render and I/O hot paths are already peppered with `p` points, so you can profile a real session
with no code changes.

[IMPORTANT]
====
`p` and `profile` are *compile-time gated* on the `fulcro.tui.perf` system property. Unless it is
set *when the code is loaded*, they expand to just their body — zero overhead, nothing compiled
in. So the instrumentation is safe to leave in shipped code; you turn it on by setting the
property at launch.
====

== Turning it on

Set `fulcro.tui.perf` (to anything) when you start the app:

[source,bash]
-----
bb -Dfulcro.tui.perf=1 tui              # babashka
clojure -J-Dfulcro.tui.perf=1 -M:tui    # JVM
-----

== The automatic session report

`run-blocking!` (and therefore `start!`) wraps the whole session in `perf/profile`. With the
property set, the entire interactive session is profiled and a self-time table is printed to
stdout *after you quit* — `mount!` restores the terminal first, so the table lands cleanly in
your scrollback. The workflow:

. Launch with the property set (above).
. *Exercise the paths you care about* — scroll the list, type in the notes box, open the
  picker/modal. The profiler only sees what you actually do.
. Quit with *Ctrl-Q*.
. Read the table that prints.

== Reading the report

A trimmed example:

[source]
-----
id                                  nCalls    self% self(ms)  mean(µs)   p50(µs)   p99(µs)  total(ms)
----------------------------------------------------------------------------------------------------
:io/read-key                            29    73.5  1310.20   45179.2   20086.6  405113.0    1310.20
:paint/vbox                             46     7.3   129.95    2825.1    4231.7   23277.8     276.37
…/engine/row-ops                       989     5.0    89.23      90.2      87.8     150.6      89.23
…/engine/put-str                       782     3.5    62.54      80.0      38.3     335.0      62.54
…/application/render!                   23     0.4     7.00     304.3     312.8     355.4     424.37
…/engine/diff                           23     0.2     3.20     139.0     125.8     262.9      92.43
----------------------------------------------------------------------------------------------------
Σ self = 1783.02 ms across 32 ids; wall = 1489.86 ms
-----

[cols="1,4"]
|===
| Column | Meaning

| `id` | The profile point — a render stage (`:paint/vbox`, `…/row-ops`, `…/diff`, `…/render!`) or an I/O point (`:io/read-key`, `:io/write`, `:io/flush`).
| `nCalls` | How many times it ran during the session.
| `self%` / `self(ms)` | *Exclusive* time: this point minus everything nested inside it. This is where CPU time actually went; rows are sorted by it.
| `mean` / `p50` / `p90` / `p99` / `max(µs)` | The per-call distribution of *self* time.
| `total(ms)` | *Inclusive* time: this point including all nested points.
|===

Three things to keep in mind:

* *Ignore `:io/read-key`.* It is almost always the biggest row, but it is *idle* time — the loop
  blocking for your next keystroke, not work. It measures how long you sat there, not how slow
  anything is.
* *self vs. total.* `self` is exclusive of nested points; `total` is inclusive. A wrapper like
  `render!` has tiny `self` (its own glue) but large `total` (the whole frame). For a leaf stage
  the two are equal; for a wrapper, read `total`.
* *Whole-frame cost lives in `total`.* The `mean`/`p99` columns are *self* time, so they do not
  show a wrapper's end-to-end cost. To baseline a full frame, read `render!`'s `total(ms)`
  divided by its `nCalls`; the per-stage `self%` rows then tell you where inside that frame the
  time went (typically paint/layout — `row-ops`, `put-str`, `vbox` — not the ANSI serialization).

== Measuring in the REPL or a test

You can scope a measurement around any call. The property must still be set *when the namespaces
were loaded*, so start the REPL/bb process with it:

[source,clojure]
-----
(require '[com.fulcrologic.fulcro.tui.perf :as perf]
         '[com.fulcrologic.fulcro.tui.application :as app])

;; Bracket one call: prints a report, returns the body value.
(perf/profile {} (app/render! app))

;; …or drive it by hand:
(perf/start!)                       ; enable + reset
(dotimes [_ 100] (app/render! app))
(perf/report)                       ; print the table
(perf/stop!)                        ; disable
-----

`perf/snapshot` returns the raw stats map (id -> aggregate) if you want to assert on it
programmatically (e.g. in a test).

== Instrumenting your own code

Wrap any expression in `perf/p` with an id (a keyword or a syntax-quoted symbol):

[source,clojure]
-----
(require '[com.fulcrologic.fulcro.tui.perf :as perf :refer [p]])

(p :my/expensive-step
  (do-expensive-thing ...))
-----

It records both inclusive and self (exclusive of nested `p`) time, so it is safe to wrap
recursive code. Like the built-in points it is compile-time gated, so it costs nothing in a
build that did not set `fulcro.tui.perf`.

NOTE: `perf` also provides a babashka-safe, optionally TTL-expiring memoizer (`perf/cache` /
`perf/memoize`) used by the layout caches — unrelated to profiling, but it lives in the same
namespace because it, too, had to be reimplemented to run under SCI.

= Testing / Headless

The library is built to be exercised without a real terminal: a fake terminal plus a
deterministic single-step driver let you assert on exactly what would be painted.

== The pieces

* `term/string-terminal` — an atom-backed fake `Terminal`. Construct it with `:rows`,
  `:cols`, and (optionally) a scripted seq of `:keys` that `t-read-key` dequeues in
  order. Inspect it with `term/output` and `term/cursor`; drive it with `term/feed!`
  and `term/resize!`.
* `app/attach!` — attach the fake terminal and do the initial paint (no input loop).
* `app/step!` — dispatch one key event and repaint, deterministically.
* `app/screen-of` / `app/screen-styled-of` — read the most-recently-painted buffer
  back as row strings (or styled cell maps) for assertions.
* `engine/current-focus`, `engine/get-caret`, `engine/viewport-scroll` — read focus,
  caret, and scroll state.
* `term/key-event` builds a normalized key event; a key event is just a map
  (`{:key … :char … :ctrl? …}`), so tests usually write the map literal directly.

== A worked example

This mirrors the library's own `application-spec`. A root with a single input:

[source,clojure]
-----
(ns my.tui-test
  (:require
    [com.fulcrologic.fulcro.components :as comp]
    [com.fulcrologic.fulcro.mutations :as m]
    [com.fulcrologic.fulcro.tui.elements :as elements]
    [com.fulcrologic.fulcro.tui.engine :as engine]
    [com.fulcrologic.fulcro.tui.application :as app]
    [com.fulcrologic.fulcro.tui.terminal :as term]
    [clojure.string :as str]
    [clojure.test :refer [deftest is]]))

(m/defmutation set-a [{:keys [v]}]
  (action [{:keys [state]}] (swap! state assoc :app/a v)))

(comp/defsc Root [this {:keys [app/a]}]
  {:query         [:app/a]
   :initial-state {:app/a ""}}
  (elements/vbox {:id "root"}
    (elements/input {:id        :a
                     :value     a
                     :on-change (fn [v _caret] (comp/transact! this [(set-a {:v v})]))})))

(deftest typing-updates-state-screen-and-caret
  (let [app (app/application {:root-class Root})        ; :initial-state on by default
        t   (term/string-terminal {:rows 4 :cols 12})]
    (app/attach! app t)                                  ; initial paint; focus -> :a
    (app/step! app {:key "H" :char "H"})
    (app/step! app {:key "i" :char "i"})
    (let [state @(:com.fulcrologic.fulcro.application/state-atom app)]
      (is (= "Hi" (:app/a state)))                       ; the :on-change tx updated state
      (is (str/starts-with? (nth (app/screen-of app) 0) "Hi")) ; row 0 shows the typed text
      (is (= 2 (engine/get-caret app :a 0)))             ; caret advanced by 2
      (is (= {:x 2 :y 0 :visible? true} (term/cursor t)))))) ; hardware cursor follows
-----

== Scripting the input loop

You can also script keys onto the terminal and run the *real* loop to completion; it
ends when `t-read-key` returns nil (the queue drains):

[source,clojure]
-----
(let [app (app/application {:root-class Root})
      t   (term/string-terminal {:rows 4 :cols 12
                                 :keys [{:key "H" :char "H"} {:key "i" :char "i"}]})]
  (app/run-blocking! app {:terminal t})   ; processes both keys, then the loop ends
  (is (= "Hi" (:app/a @(:com.fulcrologic.fulcro.application/state-atom app))))
  (is (true? (:left? @(.-state t)))))      ; the loop left the terminal on exit
-----

NOTE: The bundled specs under `src/test/com/fulcrologic/fulcro/tui/`
(`application_spec.clj`, `engine_spec.clj`, `elements_spec.clj`, and
`terminal_spec.clj`) use `fulcro-spec` rather than `clojure.test` and cover focus,
typing, activation, viewport scrolling, multiline editing, overlays/pickers, and the
input loop. They are the most complete worked reference.

= Extending: custom rendered elements

== Compose first

Almost every UI need is met by *composing* the built-in elements inside an ordinary `defsc`
component — a labeled field, a status bar, a card, a list row are all `vbox`/`hbox`/`box`/`text`
arrangements. Reach for a brand-new low-level element only for a genuinely new *painting primitive*:
something no arrangement of `text`/`box`/`line` can express (a sparkline, a gauge/bar, a custom
glyph block). Composition needs no engine changes; a new primitive does.

== The three render seams

The engine resolves three per-tag rendering decisions through multimethods on `::engine/tag`, each
with a fast built-in path and an open `:default`. To add a rendered tag, `defmethod` the ones you
need:

[cols="1,4"]
|===
| Multimethod | Implement it to…

| `engine/content-size` | report your tag's natural `{:w :h}` (before the node's own `:width`/`:height`/`:min-*` overrides). Optional — omit it and just set `:width`/`:height` on the node.
| `engine/place` | lay out a custom *container's* children. Omit for a leaf (it is given a `::rect` automatically).
| `engine/paint` | draw your tag's cells into the buffer. Required for anything visible.
|===

A registered tag is resolved at dispatch; an *unregistered* tag is harmless — it sizes to its insets,
places as a leaf, and paints nothing (no error, no infinite loop).

== A custom leaf (a bar gauge)

[source,clojure]
-----
(ns my.widgets
  (:require
    [com.fulcrologic.fulcro.tui.elements :as elements]
    [com.fulcrologic.fulcro.tui.engine :as engine]))

;; 1. A generator that emits your tag. (`elements/element` is the generic node builder.)
(defn bar [& args] (elements/element :my/bar args))      ; e.g. (bar {:value 0.6 :width 20})

;; 2. Natural size (optional). Include your own :padding/:border? insets if you support them.
(defmethod engine/content-size :my/bar [_] {:w 10 :h 1})

;; 3. Paint: fill `:value` (0.0–1.0) of the width with a solid block, the rest with a light one.
(defmethod engine/paint :my/bar [buf node clip]
  (let [{:keys [x y w]} (::engine/rect node)
        style  (engine/node-style (::engine/attrs node))
        filled (long (* (double (or (:value (::engine/attrs node)) 0.0)) w))]
    (reduce (fn [b i]
              (if (engine/in-clip? clip (+ x i) y)
                (engine/put-cell b (+ x i) y (if (< i filled) \█ \░) style)
                b))
      buf (range w))))
-----

Now `(bar {:value 0.6 :width 20 :color :green})` renders anywhere a built-in element does.

NOTE: The painter toolkit a `paint` method may use is all public in `engine`: `put-cell`, `put-str`,
`fill-rect`, `draw-border`, `blit`, plus the geometry/style helpers `node-style`, `content-rect`,
`rect-intersection`, and `in-clip?`. To paint child nodes, call `engine/paint` recursively.

== A custom container (reusing the built-in layout)

A container needs BOTH a `place` (lay children out) and a `paint` (recurse into the placed children).
Rather than reimplement distribution, reuse `engine/place-stack` — the same `:vbox`/`:hbox` engine
that honors `:width`/`:height`/`:half`/`:fraction`/`:grow`/`:align`:

[source,clojure]
-----
(defmethod engine/place :my/grid [node rect]
  (let [{:keys [l r t b]} (engine/edge-insets (::engine/attrs node))   ; honor own padding/border
        content {:x (+ (:x rect) l) :y (+ (:y rect) t)
                 :w (max 0 (- (:w rect) l r)) :h (max 0 (- (:h rect) t b))}]
    (assoc node ::engine/rect rect
      ::engine/children (engine/place-stack :v content
                          (mapv engine/as-node (::engine/children node))))))

(defmethod engine/paint :my/grid [buf node clip]
  (let [node-clip (engine/rect-intersection clip (::engine/rect node))]
    (reduce (fn [b child] (engine/paint b child node-clip)) buf (::engine/children node))))
-----

For fully custom layout, skip `place-stack` and compute each child's rect yourself, calling
`engine/place` per child. `engine/as-node` coerces bare string/number children into text nodes.

== Focus and input

A custom element joins the keyboard focus ring by carrying `:focusable? true` (and an `:id`) — no new
tag machinery is needed; see <<_buttons_focus_keyboard,Buttons, Focus & Keyboard>>. Text *input* is
intentionally NOT extensible: editable fields are the built-in `:input`, and the typing/caret
pipeline is closed. Build interactive widgets by handling activation (`:on-activate`) and reading
state, not by inventing a new input type.

= Reference: Namespaces at a glance

The library is six namespaces under `com.fulcrologic.fulcro.tui.*`:

[cols="2,3"]
|===
| Namespace | Role

| `com.fulcrologic.fulcro.tui.elements` (`elements`)
| Element generators (`element`, `vbox`, `hbox`, `box`, `text`, `input`, `button`, `line`, `viewport`, `modal`, `picker`), plus `focused?`. State changes use Fulcro's own `comp/transact!` — there is no TUI-specific transact.

| `com.fulcrologic.fulcro.tui.engine` (`engine`)
| The node model, walker, layout, paint, and diff. Defines the node vocabulary (`::engine/tag`/`attrs`/`children`/`node`), `node?`, node accessors, the render pipeline (`render-tree`/`render-root`/`render-buffer`/`screen`), focus & scroll state (`focus!`, `current-focus`, `focus-order`, `focusables`, `get-caret`, `viewport-scroll`, `*current-focus*`), and helpers (`string-width`, `palette`, `key-chord`). The per-tag render seams `content-size`/`place`/`paint` are multimethods on `::engine/tag` — `defmethod` them to add a custom rendered element (see <<_extending_custom_rendered_elements,Extending>>), using the public painter/layout toolkit (`put-cell`, `put-str`, `fill-rect`, `draw-border`, `blit`, `node-style`, `content-rect`, `rect-intersection`, `in-clip?`, `place-stack`, `as-node`, `edge-insets`).

| `com.fulcrologic.fulcro.tui.application` (`app`)
| The application lifecycle and terminal driver: `application`, `attach!`, `mount!`, `run-blocking!`, `quit!`, `step!`, and the inspection helpers `screen-of`/`screen-styled-of`.

| `com.fulcrologic.fulcro.tui.terminal` (`term`)
| The terminal abstraction: the `Terminal` protocol, `jline-terminal`, the `string-terminal` fake, the normalized key-event model (`key-event`, `special-keys`), and the pure key decoder (`decode-key`).

| `com.fulcrologic.fulcro.tui.inspect` (`tui-inspect`)
| Debug-only Fulcro Inspect connector (`add-inspect!`, `install!`, `enable!`). Ships in `src/main` but is loaded lazily, only when inspect is enabled.

| `com.fulcrologic.fulcro.tui.perf` (`perf`)
| Built-in, babashka-safe profiler (`p`, `profile`, `start!`/`stop!`/`report`, `snapshot`) — compile-time gated on the `fulcro.tui.perf` property, so zero overhead when off. Also a bb-safe memoizer (`cache`/`memoize`). See <<_measuring_performance,Measuring performance>>.
|===

== Dependency direction

The namespaces form an acyclic graph:

* `elements` → `engine`
* `application` → `engine` + `elements` + `terminal` (+ `perf`)
* `engine` → `perf`
* `terminal` → `perf`
* `perf` — standalone (no dependency on the others)
* `inspect` — loaded lazily by `application` only when inspect is enabled
